## 0. 무엇이 문제인가 — 원인은 스키마 한 줄이다

라이브 실측(`/blog/unsold-housing-briefing-2026-08-04`, HTTP 200) 결과 `href="/blog/<slug>"` 형태가 **0개**다 [인용: 라운드58 §6]. 네비·브레드크럼의 `/blog` 4개와 `sourceLinks`의 외부 뉴스 3개가 그 페이지 본문 링크의 전부다.

원인은 코드로 확인된다 [확인]:

| 층 | 사실 | 근거 |
|---|---|---|
| 데이터 | `BlogSection` 6개 타입 중 인라인 링크를 담을 수 있는 것이 없다. `paragraph.text`는 순수 `string` | `lib/blog.ts:31-47` |
| 렌더 | `BlogBody`가 그 유니온을 순수 switch로 매핑한다. `<a>`는 `sourceLinks` 케이스 하나뿐 | `BlogBody.tsx:14-100`, 앵커는 `:77-84` |
| 페이지 | 상세 페이지에 관련글 컴포넌트가 없다. `getBlogPosts`는 목록에서만 쓰인다 | `app/blog/[slug]/page.tsx` 전체 |

**그런데 링크할 문장은 이미 본문에 다 쓰여 있다.** 발행본에 다른 글을 지칭하는 평문이 **10곳** 존재한다(§6-1). 라운드29 이후 "타입이 없으니 제목만 언급한다"는 관행이 굳어져 생긴 것이고, 그 관행 자체가 축자 중복 게이트의 주된 잔여 원인이라는 기록도 이미 있다(`docs/team-log/2026-07-29.md:91,153`, `2026-08-01.md:158`). **즉 이번 작업은 "링크를 새로 만드는 일"이 아니라 "이미 있는 지칭을 클릭 가능하게 만드는 일"이다.** 이 사실이 아래 모든 설계 판단의 전제다.

## 1. 표현 방식 — **(b) `paragraph`에 `segments` 추가, 권고**

### 1-1. 권고안 타입 (개발팀이 그대로 옮길 형태)

```ts
/**
 * 본문 문단 안의 조각 하나.
 * slug가 있으면 /blog/<slug> 내부링크, 없으면 평문.
 * 🔴 href·url 필드를 만들지 마라 — 외부 URL은 이 수단으로 넣을 수 없다(§3-1).
 */
export type BlogInlineSegment = {
  text: string;
  /** 같은 사이트 블로그 글의 slug. 경로·쿼리·해시·프로토콜을 넣지 않는다(§3-1). */
  slug?: string;
};

export type BlogSection =
  // 기존 문단 — 발행본 16편이 쓰는 형태. 🔴 이 줄을 고치지 마라.
  | { type: "paragraph"; text: string; segments?: never }
  // 신규: 인라인 링크가 있는 문단. text와 상호배타.
  | { type: "paragraph"; segments: BlogInlineSegment[]; text?: never }
  | { type: "heading"; text: string }
  | { type: "list"; ordered?: boolean; items: string[] }
  | { type: "callout"; variant: "info" | "warning"; text: string }
  | { type: "sourceNote"; asOfDate: string }
  | { /* sourceLinks — 현행 그대로, 변경 없음 */ };
```

렌더 헬퍼 2개를 함께 둔다(둘 다 신규, add-only):

```ts
// lib/blog.ts — 문단의 순수 텍스트. 읽기시간 계산·불변식 검증이 공유한다.
export function paragraphPlainText(section: {
  text?: string;
  segments?: BlogInlineSegment[];
}): string {
  return section.segments ? section.segments.map((s) => s.text).join("") : section.text ?? "";
}
```

```tsx
// components/blog/BlogBody.tsx — paragraph 케이스 안에서만 쓴다.
function renderParagraphContent(section: {
  text?: string;
  segments?: BlogInlineSegment[];
}): React.ReactNode {
  // segments가 없으면 문자열을 그대로 반환한다 — 기존 문단의 DOM이 완전히 동일해진다(§2-3).
  if (!section.segments) return section.text;
  return section.segments.map((seg, i) =>
    seg.slug ? (
      <Link key={i} href={`/blog/${seg.slug}`} className="text-brand underline underline-offset-2">
        {seg.text}
      </Link>
    ) : (
      seg.text
    )
  );
}
```

`paragraph` 케이스는 **하나만 유지**한다. `<p>` 클래스 문자열(`text-sm sm:text-base text-gray-600 leading-relaxed mt-4 first:mt-0`, `BlogBody.tsx:20` [확인])이 두 곳으로 갈라지는 일이 없어야 한다.

```tsx
case "paragraph":
  return (
    <p key={index} className="text-sm sm:text-base text-gray-600 leading-relaxed mt-4 first:mt-0">
      {renderParagraphContent(section)}
    </p>
  );
```

### 1-2. 왜 새 `type` 이름을 만들지 않고 `paragraph`를 확장하는가 — **컴파일러가 누락을 잡아준다**

이게 결정적 근거다. 이 저장소의 반복 사고 유형은 "소비처 한 곳을 안 고쳐 조용히 어긋나는 것"이다(`SummaryCards` 폴백 불일치, `RankingBoard` 인용 오기 등).

`BlogSection`을 소비하는 곳은 두 군데다 [확인]:

| 소비처 | 코드 | 새 `type` 이름을 추가하면 | `paragraph` 확장이면 |
|---|---|---|---|
| `BlogBody` switch | `BlogBody.tsx:15-99`, 끝에 `default: return null` | **조용히 아무것도 안 그린다.** 컴파일 통과 | 케이스가 하나뿐이라 누락 자체가 불가능 |
| `getReadingMinutes` reduce | `lib/blog.ts:1874-1882`, 끝에 `return sum` | **조용히 0자로 센다.** 읽기시간이 줄어드는데 컴파일 통과 | `section.text`가 `string \| undefined`가 되어 **`tsc --noEmit`가 즉시 에러** |

`paragraph` 확장은 **타입 시스템이 소비처 누락을 강제로 잡는 유일한 안**이다. 새 타입 이름은 두 곳 모두 조용히 통과한다. 이 사이트에서 "조용한 실패"의 비용은 이미 여러 차례 기록돼 있어, 시끄러운 실패를 택한다.

### 1-3. 🔴 `?: never` 두 개를 빼지 마라 — 빼면 타입이 안 막는다

`segments?: never` / `text?: never`가 없으면 `{ type: "paragraph", text: "…", segments: [...] }`가 **컴파일을 통과한다.** TypeScript의 초과 속성 검사는 유니온 대상에 대해 "**어느 한 멤버라도** 그 속성을 선언하면 통과"시키고, 그다음 구조적 할당은 `{type, text}` 멤버에 성립하기 때문이다 [추정: TS 사양 근거의 판단이며 이번에 컴파일러로 실증하지 않았다 — 개발팀이 반례 리터럴 1개로 5분 안에 검증할 수 있다].

두 필드가 동시에 들어오면 렌더는 `segments`만 보고 `text`는 **화면에서 사라진다.** 문단 하나가 통째로 소실되는데 빌드는 성공하는 상태다. `?: never`가 이 상태를 컴파일 에러로 바꾼다.

`BlogInlineSegment` 쪽은 반대로 **유니온을 쓰지 않는다.** `{ text } | { text, slug }`로 갈라도 `slug?: string` 하나와 정보량이 같고(부재 = 평문), 충돌할 두 번째 필드가 없어 애매함이 생기지 않는다. 단순한 쪽을 택한다.

### 1-4. 탈락안과 사유

| 안 | 판정 | 사유 |
|---|---|---|
| **(a) `paragraph.text`를 마크다운 부분집합(`[텍스트](/blog/slug)`)으로 파싱** | **기각** | ① **명시적으로 폐기된 설계 원칙을 되살린다.** `lib/blog.ts:5-7`이 *"본문은 마크다운 문자열이 아니라 구조화된 섹션 배열 … 마크다운 파서·`dangerouslySetInnerHTML`이 필요 없고 XSS 위험이 없다"*고 못 박았고, `docs/design/blog.md` §7-6이 이탤릭 요구를 이 원칙 때문에 **기각한 선례**가 있다 [확인]. 파서를 들이면 그 기각 근거가 소급해서 무효가 된다. ② **회귀 위험이 데이터 의존이다.** 현재 `text:` 한 줄 문자열에 `[`가 0건이라 오탐이 없어 보이지만 [확인], 괄호는 36건 있고 [확인] 앞으로 원고 한 편이 각괄호를 쓰는 순간 조용히 회귀한다. "지금은 안전하다"에 기대는 안전성이다. ③ **타입 안전성 0** — 잘못된 slug·외부 URL·깨진 괄호가 전부 컴파일 통과 후 런타임에 드러난다. ④ 파서 출력이 `ReactNode` 배열이라 결국 (b)와 같은 렌더를 하면서, 문자열 파싱 단계만 더 얹는다. |
| **(c) 새 섹션 타입 `relatedInline`/`internalLink`(블록 요소)** | **차선 — 이번 라운드 미채택** | ① **문제를 해결하지 못한다.** 링크가 문장 밖 별도 줄에 서므로 §6-1의 평문 지칭 10곳은 **그대로 평문으로 남는다.** 같은 글에 "평문 지칭 + 아래에 링크 줄"이 병존해 중복이 되고, 축자 게이트의 원인이던 지칭 정형구도 그대로 남는다(`2026-07-29.md:91`). ② §1-2의 조용한 실패 2건에 그대로 노출된다. ③ 본문 끝에 붙는 단독 링크 줄은 이 페이지에서 **CTA 박스**(`page.tsx:142-155`)와 **`sourceLinks` 블록**(`BlogBody.tsx:70-95`) 사이에 끼어, `blog.md` §7-2가 참고 기사에 카드형을 기각했던 것과 같은 위계 혼란을 만든다. ④ 다만 **폐기는 아니다** — 훗날 "관련 글" 섹션을 정식으로 만들 때 재검토할 가치가 있다. 🔴 **단, 이번 라운드에 (b)와 함께 넣지 마라.** 같은 목적의 수단이 둘이면 편집자가 매번 어느 것을 쓸지 고민하고 실제로 혼용된다. |
| **`dangerouslySetInnerHTML`로 문단에 HTML 삽입** | **명시적 기각** | `lib/blog.ts:5-7`이 이 함수를 쓰지 않는 것을 설계 목표로 적어 두었다 [확인]. 저장소 내 유일한 사용처는 `app/blog/[slug]/page.tsx:110-115`의 JSON-LD인데, 그건 **비가시 `<script>`**이고 Next.js 공식 가이드가 지시한 `<` 이스케이프까지 붙은 패턴이라 본문 텍스트의 선례가 아니다 [확인]. 더 결정적인 것: 이 저장소의 본문 문자열은 **자동화 세션이 생성**한다. 외부 뉴스 스니펫을 재료로 쓰는 `market` 카테고리가 존재하는 상태에서 본문에 HTML 파싱 경로를 열면 XSS가 이론적 위험이 아니라 실제 경로가 된다. |

### 1-5. 이 구성안이 **하지 않는** 것

- 표·이미지·이탤릭·굵기 등 다른 인라인 서식을 함께 도입하지 않는다. `segments`는 **링크 전용**이다(서식 요구가 생기면 그때 별도 스펙 — `blog.md` §7-6이 이탤릭을 기각한 판단은 유효하다).
- `list.items: string[]`을 건드리지 않는다(§5-2).
- `callout.text`를 건드리지 않는다(§5-2).
- 상세 페이지에 "관련 글" 섹션·카드·CTA를 새로 만들지 않는다.

## 2. add-only 보장

### 2-1. 층을 나눈다 — 스키마 변경과 본문 전환은 다른 작업이다

| 층 | 기존 16편에 대한 변경 | 이번 라운드 |
|---|---|---|
| **A. 스키마 + 렌더** | **0글자.** `{type:"paragraph", text:"…"}`가 그대로 유효하고, 렌더 경로도 `segments` 부재 시 이전과 동일하다 | 필수 |
| **B. 본문 전환** | 지정한 문단 **10개**가 `text` → `segments`로 형태만 바뀐다. 가시 문자열은 불변(§2-3) | 권고(§6-1) |
| **C. 신규 링크 추가** | 새 문장·새 어구가 들어간다 | **이번 라운드 밖.** 기획팀 문안 필요(§6-2) |

A만 반영하고 B를 안 해도 빌드는 통과하고 화면은 지금과 동일하다. **A와 B는 같은 커밋에 넣어도 되지만, B를 먼저 하는 것은 불가능하다**(타입이 없으므로).

### 2-2. 타입 수준 보장

- 기존 항목이 새 필드를 **요구받지 않는다** — `segments?: never`는 "있으면 `undefined`여야 한다"이고 부재는 정상이다.
- 기존 항목이 새 형태로 **오인되지 않는다** — `text`가 있는 멤버와 `segments`가 있는 멤버가 상호배타라 섞인 객체는 컴파일 에러(§1-3).
- 새 형태가 **기존 렌더를 바꾸지 않는다** — `renderParagraphContent`가 `segments` 부재 시 `section.text`를 **그대로** 반환한다(배열로 감싸지 않는다).

### 2-3. 가시 텍스트 불변식 — 이것이 B층의 유일한 합격 기준

```
segments.map(s => s.text).join("")  ===  전환 전 text 문자열
```

**한 글자의 차이도 허용하지 않는다.** 공백·구두점·작은따옴표·가운뎃점 전부 포함이다. 이 불변식이 성립하면 다음이 자동으로 따라온다:

1. 화면에 보이는 문장이 전환 전후 완전히 동일하다 → 콘텐츠 재검수 불필요.
2. `getReadingMinutes` 값이 16편 전부 불변 → 메타 줄의 "읽는 시간 N분"이 안 흔들린다(`page.tsx:137` [확인]).
3. 축자 중복 게이트의 측정값이 안 변한다 → QA 재판정 불필요.
4. `summary`·`title`·`meta description`은 애초에 손대지 않으므로 SEO 텍스트 변화 0.

**검증 절차(권고, 10곳이라 수동 대조는 실수한다):**

```
git show HEAD:lib/blog.ts  로 전환 전 문자열을 뽑아
전환 후 paragraphPlainText(section) 와 문자열 비교 → 10/10 일치
```

`paragraphPlainText`(§1-1)를 그 대조에 그대로 쓸 수 있게 `export`한다. 일회용 스크립트는 커밋하지 않아도 된다.

### 2-4. 🔴 파급 소비처 전수 — 이 3곳을 같이 안 고치면 조용히 깨진다

## 3. 링크 유효성

### 3-1. 내부 경로만 허용 — **타입에서 막는다**

**결정: `BlogInlineSegment`는 `slug`만 받는다. `href`·`url` 필드를 두지 않는다.** `BlogBody`가 `` `/blog/${seg.slug}` ``로 조립하므로 외부 URL·프로토콜·`javascript:`·상대경로 탈출이 **구조적으로 표현 불가능**하다.

외부 링크를 이 수단으로 넣지 못하게 하는 이유:

1. **출처 표기 원칙이 흐려진다.** `content-strategy.md` §7-3-1(출처 흐리기 금지)·§7-3-9(출처 목록 없는 뉴스 종합 글 미발행)·§7-6(6단계: 공공데이터 캡션 vs 뉴스 목록을 **표기 위치·형식으로 분리**)이 외부 출처를 `sourceLinks` 한 곳에 모으도록 설계돼 있다 [확인]. 본문 문장 속 외부 링크를 허용하면 매체명·기사 제목·발행일 3요소를 우회하는 경로가 생긴다.
2. **접근성 처리가 갈린다.** 외부 링크는 `target="_blank" rel="noopener noreferrer"` + `<span class="sr-only">(새 탭에서 열림)</span>`가 필수인데(`blog.md` §7-3, `BlogBody.tsx:79-85` [확인]), 내부 링크는 그 처리를 하면 안 된다. 한 필드로 둘을 다루면 렌더에 분기가 생기고 편집자가 틀린다.
3. **YMYL.** 외부 사이트로 본문에서 직접 내보내는 링크는 이 사이트가 그 내용을 보증하는 것처럼 읽힐 수 있다. `sourceLinks`는 "우리가 재료로 쓴 기사"라는 맥락이 블록 자체에 붙어 있어 그 오인을 막는다.

🔴 **금지(개발팀·후속 라운드 공통)**

- `slug` 값에 `/`, `?`, `#`, `http`, `..`가 들어가는 것. 전부 §3-2 검증에서 걸러야 한다.
- `BlogInlineSegment`에 `href`·`url`·`external`·`target` 필드를 추가하는 것. 필요가 생기면 `sourceLinks`를 쓰거나 별도 스펙을 세운다.
- 링크에 `target="_blank"`를 붙이는 것. 내부 이동이다.
- 앵커(`#section`)·쿼리스트링을 붙이는 것. 블로그 상세에는 앵커 대상 id가 없다 [확인: `BlogBody`의 `heading`에 `id` 없음].

### 3-2. 빌드 타임 검증 — **`lib/blog.ts` 모듈 초기화 시 throw**

`getBlogPostBySlug`가 이미 있으므로(`lib/blog.ts:1851-1853` [확인]) 검증 함수는 그 위에 얹는다.

```ts
// lib/blog.ts, blogPosts 배열 정의 직후
function validateBlogInternalLinks(): void {
  const slugs = new Set(blogPosts.map((p) => p.slug));
  for (const post of blogPosts) {
    for (const section of post.body) {
      if (section.type !== "paragraph" || !section.segments) continue;
      for (const seg of section.segments) {
        if (!seg.slug) continue;
        if (!/^[a-z0-9-]+$/.test(seg.slug)) throw new Error(`blog: 잘못된 slug 형식 ${post.slug} → ${seg.slug}`);
        if (!slugs.has(seg.slug))          throw new Error(`blog: 없는 글로 가는 링크 ${post.slug} → ${seg.slug}`);
        if (seg.slug === post.slug)        throw new Error(`blog: 자기 자신을 링크 ${post.slug}`);
        if (!seg.text.trim())              throw new Error(`blog: 링크 텍스트가 비었다 ${post.slug} → ${seg.slug}`);
      }
    }
  }
}
validateBlogInternalLinks();
```

**왜 모듈 초기화 시 throw인가**

- `blogPosts`는 정적 배열이고 `/blog/[slug]`는 `generateStaticParams`로 전량 SSG된다(`page.tsx:20-22` [확인]). 따라서 **`next build`가 이 모듈을 import하는 순간 검증이 돌고, 실패하면 빌드가 죽는다.** 죽은 링크가 라이브에 나갈 경로가 없다.
- `generateStaticParams`가 모든 slug의 페이지를 만들므로 **"`blogPosts`에 있는 slug"는 곧 "실제 200 응답하는 페이지"**다. 파일 시스템이나 HTTP 확인이 따로 필요 없다 [확인].
- 빌드가 통과하면 데이터가 정적으로 고정되므로 **런타임에는 절대 throw할 수 없다.** 프로덕션 위험이 없다.
- 🔴 **`process.env.NODE_ENV !== "production"` 가드를 붙이지 마라.** `next build`는 production 모드로 돌기 때문에 그 가드를 붙이면 **게이트가 통째로 무력화**된다. 이 프로젝트에서 조용한 실패가 반복 관측된 지점이 정확히 이런 형태다.
- 16편 × 문단 수 = 수백 회 루프이므로 비용은 무시할 수준 [추정: 실측 안 함, 산술 판단].

대안(모듈 초기화 throw를 마스터가 원치 않을 경우): `scripts/`에 검증 스크립트를 두고 `prebuild`로 거는 방식. 다만 이 저장소에는 `test`·`prebuild` 스크립트가 없어(`package.json:5-10` [확인]) 새 관행을 하나 만드는 셈이고, 스크립트는 잊고 우회하기 쉽다. **디자인팀 권고는 모듈 초기화 throw.**

### 3-3. 링크 개수 상한도 여기서 막을 것인가

**막지 않는다.** 개수 상한(§5-1)은 편집 판단이라, 코드가 강제하면 정당한 예외가 생겼을 때 스키마를 고쳐야 한다. 대신 §8 체크리스트에 카운트 항목을 둔다.

## 4. 접근성 · 시각 표기

### 4-1. 스타일 — 신규 스타일 **발명 0**

```
text-brand underline underline-offset-2
```

`app/support/page.tsx:76,102` · `app/privacy/page.tsx:88,156,170,181` · `components/RankingBoard.tsx:136`가 쓰는 **저장소 내 기존 문자열 그대로**다 [확인]. `2026-08-01-ranking-blog-link-design.md` §1-7이 "본문 문장 안 인라인 내부 링크" 유형으로 이미 승계 확정한 클래스이며, 이번 건이 그 유형의 두 번째 적용이다.

**`sourceLinks` 렌더와의 대조 (`BlogBody.tsx:81` 실제로 읽고 대조함 [확인])**

| | 본문 인라인 내부링크(신규) | `sourceLinks` 외부 출처링크(기존) |
|---|---|---|
| 클래스 | `text-brand underline underline-offset-2` | `text-gray-600 underline underline-offset-2 hover:text-brand` |
| 평시 색 | **브랜드 블루 #3f51b5** | **회색 #4a5565** <!-- 2026-08-05 정정: 원문 #4b5563은 v3 기준값. v4가 gray-600을 재정의해 실측은 #4a5565 (라이브 계측) --> |
| 밑줄 | 항상 | 항상 |
| 위치 | 본문 `<p>` 안 | `mt-10 pt-6 border-t` 구분선 아래 별도 블록 |

**두 링크는 색으로 갈린다. 이것이 의도다.** 회색 밑줄은 이 컴포넌트에서 이미 "외부 출처 각주" 톤으로 확립돼 있고(`blog.md` §7-2 "각주·인용목록에 가깝다"), 같은 회색을 본문 내부링크에 쓰면 **같은 페이지 안에서 성격이 정반대인 두 링크가 시각적으로 동일**해진다. `2026-08-01` 스펙 §1-7이 유형 ④(`BlogBody.tsx:81` 계열)를 "회색 기조는 출처 각주 전용 톤"이라며 기각한 것과 같은 판단이다.

- 대비: `#3f51b5` on `#ffffff` = **6.87:1** [인용: `2026-08-01-ranking-blog-link-design.md` §7-2 QA 실측]. WCAG AA(4.5:1) 통과, AAA(7:1) 미달. 본문은 `text-sm sm:text-base`(14/16px)라 소형 텍스트 기준이 그대로 적용되며 AA는 충족.
- **색 단독 의존 아님(WCAG 1.4.1)**: `underline`이 항상 켜져 있다. 🔴 `hover:underline`(평시 밑줄 없음) 계열로 바꾸지 마라 — 본문 문장 속에서 링크임을 놓친다.
- `hover` 상태에 클래스를 **추가하지 않는다.** 승계한 선례 7곳 전부 hover 변화가 없다 [확인]. 새로 발명하지 않는다.

### 4-2. 링크 텍스트 규칙

**무엇을 감싸는가**: 목적지 글을 가리키는 **명사구 하나**. 우선순위는 ① 목적지 제목 전문 → ② 제목의 핵심 어휘를 보존한 축약 → ③ 목적지 주제를 그대로 말하는 명사구(예: `순위표를 읽는 원칙`, `지역 데이터를 읽는 원칙`).

🔴 **금지 링크 텍스트** (WCAG 2.4.4/2.4.9 + `2026-08-01` §4-1 승계)

| 금지 | 왜 |
|---|---|
| `여기`, `여기를 클릭`, `클릭`, `이곳` | 스크린리더 "링크 목록"에서 목적지를 알 수 없다 |
| `자세히 보기`, `더 보기`, `바로가기`, `보러 가기` | 같은 이유. 게다가 이 저장소 인라인 링크 선례 7곳에 하나도 없다 |
| `이 글`, `그 글`, `해당 글`, `링크` | 지시대명사는 링크 목록에서 무의미 |
| `필독`, `꼭 확인`, `지금 확인하세요` | 클릭 유도 프레이밍. 애드센스 정책 정합 + YMYL 톤 훼손(`2026-08-01` §2-2 동일 판단) |
| 문장 전체 | 밑줄 덩어리가 문단을 지배한다. 명사구 하나만 감싼다 |

🔴 **조사(을/를/에/은/는/이/가)는 링크 밖에 둔다.** `<Link>…법</Link>에 따로 정리했습니다` 형태. 선례가 정확히 같다(`support/page.tsx:76` `<Link>이용약관</Link>을 참고해…`, `RankingBoard.tsx:136-139` [확인]). 조사를 안에 넣으면 링크 목록에서 `…법에`처럼 잘린 어절로 읽히고, 도착 페이지 h1과의 대조도 어긋난다.

🔴 **화살표(`→`)·아이콘·이모지 금지.** 이 저장소에서 화살표는 **버튼형 CTA**(`page.tsx:149` "대시보드에서 조회하기 →")와 **복귀 링크**(`page.tsx:159` "← 부동산 정보 목록으로")에만 붙는다. 인라인 텍스트 링크 선례 7곳 전부 화살표·아이콘이 없다 [확인].

🔴 **`aria-label`·`title` 속성을 붙이지 마라.** 가시 텍스트로 충분하고, 접근가능 이름이 가시 텍스트와 어긋나면 음성 제어 사용자에게 더 나쁘다(`2026-08-01` §4-1 동일 판단).

**따옴표 처리 (§6-1 전환 시 중요)** — 발행본의 지칭 5곳은 `'제목' 글이 …` 형태로 작은따옴표에 싸여 있다 [확인: `lib/blog.ts:967,1232,1763,1779,1787`]. **따옴표는 링크 밖 평문 조각으로 남긴다.** 링크 텍스트에 따옴표를 넣으면 링크 목록에서 군더더기가 되고, 따옴표를 지우면 §2-3 불변식이 깨진다. 따옴표가 링크와 중복이라 없애고 싶다는 판단은 **별건 문안 정리**로 올린다(§9).

🔴 **축약된 제목을 실제 제목으로 늘리지 마라.** 발행본의 `'같은 시·도 안에서도 구마다 평균가가 다르게 보이는 이유'`는 실제 제목(`… 이유 — 지역 데이터를 오해 없이 읽는 원칙`)의 축약이고, `'6월 서울 아파트 전세 거래 건수, 아직 확정된 숫자가 아닙니다'`도 실제 제목의 `시황 브리핑 — ` 접두를 뺀 축약이다 [확인]. **의도된 축약이며 그대로 감싼다.** 늘리면 가시 텍스트가 바뀌어 §2-3이 깨지고, 모바일에서 3줄이 된다.

### 4-3. 줄바꿈 거동

- 링크 텍스트가 줄바꿈 경계에 걸려 두 줄로 쪼개질 수 있다. **정상이고, 별도 처리를 하지 않는다.** 같은 조건이 `support/page.tsx`에서 이미 라이브다 [확인].
- 🔴 **`whitespace-nowrap`을 붙이지 마라.** `app/globals.css:49-50`의 전역 `word-break: keep-all; overflow-wrap: break-word`가 어절 단위 줄바꿈을 보장하는데, `nowrap`은 그 방어를 무력화해 좁은 화면에서 컨테이너 밖으로 넘친다. `2026-08-01` 스펙 §7 N4가 "폭 ÷ 글자폭 단순 나눗셈" 계산법이 이 전역 규칙 때문에 **방법 오류**였다고 사후 정정한 바 있다 — 그 계산법도 재사용하지 않는다.
- 🔴 **`truncate`·`line-clamp` 금지.** 본문 문단에 붙일 이유가 없고, 링크 텍스트가 잘리면 목적지 식별이 깨진다.

### 4-4. 포커스 · 터치 타깃

- **포커스 링: 미적용(브라우저 기본) 권고.** 근거: ① 같은 컴포넌트의 형제 앵커(`BlogBody.tsx:77-84` `sourceLinks`)에 명시 포커스 링이 없다 — 여기에만 붙이면 **`BlogBody` 한 파일 안에서 링크 스타일이 두 갈래**가 된다. ② `2026-08-01` 스펙 §5-3이 같은 결론(미적용, support 계열 다수 승계)을 내리고 "인라인 링크 포커스 스타일 통일"을 별건 티켓으로 올려 둔 상태다(§6-⑤(b)) — 이번 건이 그 티켓의 난이도를 올리지 않는다. ③ 브라우저 기본 포커스 링으로도 WCAG 2.4.7 최저선은 충족한다.

    `focus-visible:outline focus-visible:outline-2 focus-visible:outline-brand focus-visible:rounded` [확인: `AptDetailModal.tsx:505,542,653,760`]

### 4-5. 반응형 · 레이아웃 영향

**레이아웃 변화 없음.** 새 DOM 요소는 `<p>` 안의 `<a>` 1~3개뿐이고, 문단 수·순서·간격(`mt-4 first:mt-0`)·클래스가 전부 그대로다. 문단 높이가 늘어날 수 있는 유일한 경우는 링크 텍스트가 줄바꿈을 한 칸 밀어 문단이 1줄 늘어나는 것인데, 밑줄은 인라인 박스 안에 그려지므로 행 높이 자체는 변하지 않는다 [추정: CSS 인라인 박스 성질에 근거, 실렌더 미측정].

| 뷰포트 | 컨테이너 | 판정 |
|---|---|---|
| 데스크톱(≥768px) | `max-w-3xl mx-auto px-4`(`page.tsx:108` [확인]) → 본문 폭 최대 704px | 문단 흐름 변화 없음 |
| 모바일 360px | 360 − 16×2 = 328px | 동일. 넘침은 전역 `overflow-wrap`이 방어(§4-3) |

## 9. 마스터께 올리는 사항

1. **순서는 지켜졌다.** 개발팀이 먼저 구현하지 않았고, 구성안이 먼저 나간다. 라운드57 W-5·라운드58 §6이 결함을 실측으로 확정했고 이 문서가 그에 대한 디자인팀 응답이다.
2. **`internalLink` 이월 안건의 형태를 바꿨다 — 확인 요청.** 라운드29에 기획팀이 제안하고 마스터가 "수요 3건 누적 시 도입"으로 대기시킨 안은 `{ type: "internalLink"; slug; label }`(블록 요소)였다(`blog-sejong-jeonse-briefing.md:292`). 이 문서는 **그 안을 채택하지 않고** `paragraph.segments`(인라인)로 바꿔 권고한다. 이유: 블록 안은 발행본의 평문 지칭 10곳을 **그대로 평문으로 남겨** 결함을 해결하지 못하고(§1-4 (c)), 소비처 누락이 컴파일 에러 없이 조용히 통과한다(§1-2). 이월 안건의 이름이 바뀌므로 폐기/대체 여부를 확정해 주시기 바란다.
3. **§6-1(10곳 전환)과 §6-2(신규 8쌍)를 분리했다.** §6-1만으로 라이브 내부링크 0 → 10이 되고 콘텐츠 재검수 비용이 0이다. §6-2는 문안 작업이라 기획팀 착수 승인이 필요하다. **한 라운드에 둘을 묶는 것은 권하지 않는다.**
4. **포커스 링 미적용을 권고한다(§4-4).** `2026-08-01` 스펙 §6-⑤(b)가 올려 둔 "인라인 링크 포커스 스타일 통일" 별건 티켓이 아직 살아 있고, 이번 건은 그 티켓의 분기를 늘리지 않는 쪽을 택했다. 명시 링을 원하시면 `BlogBody`의 **두 앵커에 동시에** 적용해야 한다.
5. **`M1`은 링크 대상에서 제외했다(§6-3).** 억지 연결을 만들지 않는다는 원칙에 따른 판단이며, 마스터가 특정 연결을 지정하면 재검토한다.
