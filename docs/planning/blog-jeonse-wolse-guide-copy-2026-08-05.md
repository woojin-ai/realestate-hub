## 1. 주제 확정 근거 + 기존 16편과 겹치지 않음 증명

### 1-1. 코드로 재확인한 사실 (본문의 뼈대)

마스터가 준 5개 사실을 전부 독립 재확인했다. **인용 위치는 지시서 §3의 각 문단에 다시 적었다.**

| # | 주장 | 재확인 결과 | 근거 위치 |
|---|---|---|---|
| 1 | 월차임 0원이면 전세, 1원이라도 있으면 월세 | ✅ 참 | `lib/molit-api.ts:385` — `const rentType: "전세" \| "월세" = monthly === 0 ? "전세" : "월세";` |
| 1-b | 이 규칙은 국토부 응답값을 그대로 쓴 것 | ✅ 참 | 같은 파일 `:368-377` — `item.deposit` / `item.monthlyRent`를 각각 파싱해 `deposit`·`monthly`로 담고, 값이 비면 0. 우리 쪽 재계산·합산 없음 |
| 2 | 반전세는 전부 "월세"로 분류된다 | ✅ 참(1의 논리적 귀결) | 보증금 크기는 `:385` 판정식에 등장하지 않는다. 코드·DB 어디에도 `반전세` 문자열 0건 [확인: 전 저장소 grep] |
| 3 | 월세 레코드는 수집·저장까지는 된다 | ✅ 참 | `lib/molit-api.ts:433-437`(`MonthData.월세`)·`:460-463`(`collectMonth`이 `deal_type`으로 갈라 담음) / `lib/db-cache.ts:227`(월세 행까지 upsert)·`:314`(읽을 때 `월세` 버킷으로 복원) / `supabase/schema.sql:14`(`check (deal_type in ('매매','전세','월세'))`) |
| 4 | `lib/analyzer.ts`에 월세 집계가 하나도 없다 | ✅ 참 | 저장소 전체 `월세` grep에서 `lib/analyzer.ts` 히트 **0건**. 대신 `:283`·`:358`·`:481`·`:515`가 전부 `"매매" \| "전세"`로 하드타입되어 있고, `lib/types.ts:8`은 `export type DealType = "매매" \| "전세";` — **유니온에 월세가 아예 없다** |
| 5 | 전세 평균에 월세 보증금이 섞이지 않는다 | ✅ 참 (단, 이유는 아래 정정) | `buildMonthlyStats`(`analyzer.ts:287`)가 `monthData["전세"]` 버킷만 읽는다. 즉 **분리는 술어가 아니라 버킷 구조가 만든다** |

🔴 **마스터 보고문 1건 정정 [확인]**: 마스터 메모는 "`isJeonseAvgSample`(`:224-233`)이 `deal_type === "전세"` + `deposit > 0`만 표본으로 쓴다"고 적었으나, **그 술어는 `deal_type`을 검사하지 않는다.** 실제 구현은 `lib/analyzer.ts:224-228`:

```
const isJeonseAvgSample = (r: RentRecord, onlyNew: boolean): boolean => {
  if (!(r.deposit > 0)) return false;
  if (onlyNew && r.contract_type === "갱신") return false;
  return true;
};
```

`deposit > 0`과 `갱신` 제외 두 가지뿐이다. 월세 배제는 **한 층 위에서 이미 끝나 있다** — `collectMonth`(`molit-api.ts:460-461`)와 `loadMonthFromDb`(`db-cache.ts:314`)가 `deal_type`으로 레코드를 세 버킷에 나눠 담고, `buildMonthlyStats`는 `전세` 버킷만 꺼내 쓴다. **결론(월세 보증금이 전세 평균에 안 섞인다)은 그대로 참이고 오히려 더 견고하다**(술어를 고쳐도 안 깨지는 구조적 분리다). 다만 본문에 "술어가 걸러낸다"고 쓰면 거짓이 되므로, §3의 문안은 **"애초에 후보로 들어오지 않는다"**로 썼다.

추가로 확인한 것 [확인]:
- 화면 탭 자체가 2개다 — `components/DealTypeTabs.tsx:10` `const TABS: DealType[] = ["매매", "전세"];`
- API 응답에도 월세가 없다 — `app/api/data/route.ts:263-270`은 `summary`(`Record<"매매"|"전세", …>`, `analyzer.ts:353`)와 `aptStatsMaeMae`/`aptStatsJeonse`만 반환한다. 월세 원본 레코드는 클라이언트로 나가지 않는다.
- 랭킹도 마찬가지 — `monthly_stats`는 `upsertMonthlyStats(… dealType: "매매" | "전세" …)`(`db-cache.ts:373-377`)로만 쓰이고, `lib/monthly-stats-gaps.ts:21`에 **"월세는 집계 대상이 아니다"**라는 주석이 명시돼 있다.

### 1-2. 기존 16편과 겹치지 않음 — 직접 대조한 결과

`lib/blog.ts` 16편의 제목·본문을 훑고 `월세`·`월 차임`·`반전세` 문자열을 전수 검색했다 [확인].

| 검색어 | 히트 | 어떤 맥락인가 | 새 글과의 관계 |
|---|---|---|---|
| `반전세` | **0건** | — | 이 개념을 다룬 글이 하나도 없다 |
| `월 차임` | **1건** (`:923` G4) | **임대차 신고 대상 요건**("월 차임 30만 원 초과") 맥락 | 새 글은 신고 대상 요건을 **한 글자도 다루지 않는다**(§6 배제 목록) |
| `월세` | 9건 | `:109`(G1 "전월세 거래도 30일"), `:864`·`:915`(G4 전월세 신고제=신규/갱신 구분 정보의 출처), `:1284`·`:1298`·`:1378`·`:1392`·`:1398`·`:1404`(M3 뉴스 인용·기사 제목) | 어느 것도 **전세와 월세를 가르는 기준**을 설명하지 않는다 |

> **▸ [2026-08-05 정정 · QA 라운드61 O-3]** 위 `월 차임` 행은 초판에서 **"2건(`:923` G4, `:1057` M2)"** 이라고 적었으나 **실측은 1건**이다. `lib/blog.ts:1057`(M2 `sejong-jeonse-briefing-2026-07-19`)의 문자열은 `"보증금과 차임 변동 없이 기간만 연장하는 갱신 계약은"`으로, **`월 차임`이 아니라 `차임`**이다.
> **기획팀 재현 [확인]**: `lib/blog.ts` 전문을 다시 검색해 `월 차임` 히트가 `:923`(발행본 16편 구간) **1줄** + 신규 글 구간(`:2062`·`:2066`·`:2070`·`:2078`·`:2110`·`:2118`·`:2122`·`:2142`·`:2143`·`:2147`) 10줄뿐임을 확인했고, `차임`으로 넓혀 검색했을 때만 `:1057`이 잡히는 것도 확인했다. 작업 트리의 기존 16편 구간은 QA 보고서 §1-(b)가 HEAD와 **객체 트리 완전 동일**(16/16)로 증명했으므로 이 검색은 `git show HEAD:lib/blog.ts` 검색과 동치다.
> **판정은 불변**: "새 글이 임대차 신고 대상 요건을 한 글자도 다루지 않는다"는 결론은 히트 수와 무관하다. `:1057`의 **무변동 갱신 미신고** 맥락은 사라진 것이 아니라 아래 §1-2 말미의 **M2 경계 항목**에서 그대로 다루고 있으며(그쪽이 정확한 위치다), 배제 목록(§6)도 불변이다.

**즉 "월차임 0원이 경계선"이라는 사실은 발행본 16편 어디에도 없다.** 이 사이트의 화면에 월세가 없다는 사실 자체도 서술된 적이 없다.

## 8. 마스터께 올리는 사항

1. **⚠️ slug·title 최종 확정 필요**(§2). 기획팀 권고는 `jeonse-vs-wolse-classification-guide` + `전세와 월세는 어디서 갈릴까 — 이 대시보드에 월세 탭이 없는 이유`이며, 마스터 원안을 그대로 써도 본문은 한 글자도 안 바뀐다. **결정 전에는 개발팀 착수 보류.**

3. **링크 3개**: L1 `body[9]` → `summary-cards-trend-chart-howto`, L2 `body[13]` → `jeonse-new-vs-renewal-contract-guide`, L3 `body[16]` → `molit-system-vs-dashboard-guide`. 이 글은 상한 3에 도달해 이후 발신 링크를 더 넣을 수 없다. 줄이길 원하시면 **L1을 먼저 빼거나 I1로 교체**하는 것을 권한다(§4).
4. **기획팀이 코드로 재확인하지 못한 것 3가지**(작성 시점 기준. ⚠️ **"전부 배제했다"는 이 줄의 원래 서술은 사실이 아니었다** — ②는 실제로는 본문 `body[7]`에 단정형으로 남아 있었고, 그것이 QA 라운드61 **F-1**로 적발됐다. 마스터 (a) 판정에 따라 지금은 **헤지형으로 존치**한다. 아래 ▸ 블록 참조. QA 라운드61 재검증 D-1):
   - 국토부 실거래가 공개시스템 **웹 화면**에서 월세가 어떤 메뉴·라벨로 보이는지 — 우리 코드가 증명하는 것은 **공공데이터 API 응답**에 월 차임이 들어 있다는 사실까지다. `body[15]`는 "원자료 쪽"까지만 말한다.

   **▸ [2026-08-05] 위 4-② "반전세의 통용 정의"에 대한 마스터 판정 (QA 라운드61 F-1)** — QA가 `body[7]` 1번째 문장과 `body[18].items[1]`을 "검산 불가능한 주장"으로 FAIL 처리하고 (a) 인용 / (b) 기각의 판정을 요청한 건이다. **판정 원문:**

   > **F-1 판정: (a) 인용 — 문안 수정.** `content-strategy.md` §2가 guide 카테고리에 용어 설명을 승인한 것은 맞으나, `body[18].items[1]`의 수식구는 **헤지 없이 요약 리스트에 놓인 검산 불가 정의**였다. 요약 리스트는 독자가 항목을 평면적 사실로 읽는 자리라 본문 문단보다 기준이 높다. 개념 자체는 글의 논지에 필요하므로 삭제하지 않되, `body[7]`은 단정형("…라고 부릅니다")에서 **언어 사용에 대한 진술**("…라는 표현이 쓰이기도 합니다")로 낮추고, `items[1]`은 수식구를 덜어 검산 가능한 사실만 남긴다.
