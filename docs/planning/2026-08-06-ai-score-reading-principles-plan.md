## 1. 글의 목표 독자와 한 줄 목적

- **목표 독자**: `ai-recommend-weights-howto`를 읽었거나 추천 화면을 이미 써 본 방문자 중, 카드에 뜬 **종합점수라는 숫자를 어디까지 믿고 무엇에 쓸 수 있는지** 알고 싶은 사람. 조작법을 모르는 첫 방문자는 이 글의 독자가 아니다(howto로 보낸다).
- **한 줄 목적**: **"종합점수는 단지에 붙은 성적이 아니라 그 조회·그 슬라이더 설정에서만 성립하는 계산 결과"** 라는 한 가지를 이해시키고, 그래서 점수를 어떻게 다뤄야 하는지(견주지 않기·옮겨 적지 않기·항목별로 나눠 보기)를 남긴다.
- **왜 insight인가**: 시점·지역에 묶이지 않는 상시(evergreen) 방법론이고 실제 지역명·수치 0건으로 쓸 수 있다(`content-strategy.md` §7-0-4의 insight 운영 정의와 일치).

## 2. 다루는 것 / 다루지 않는 것 (위임처 명시)

### 2-1. 다루는 것

여러 항목을 하나로 합친 **합성 점수라는 값의 성질** 하나뿐이다. 구체적으로 ① 점수가 무엇을 기준으로 만들어지는가(내 슬라이더·그 조회의 후보 풀), ② 항목마다 점수의 방향과 눈금이 어떻게 다른가, ③ 값을 확인하지 못했을 때도 점수가 매겨지는가, ④ 점수가 매겨진 단지가 전부인가.

### 2-2. 다루지 않는 것 (본문 [3] 범위 선언에 명시)

| 다루지 않는 것 | 위임처 | 위임 방식 |

## 4. 원문 직독으로 새로 확인한 사실 (마스터 목록에 없던 것)

기획 과정에서 코드를 끝까지 따라가며 확인했다. **A·B는 본문에 넣을 것을 권고**하고, **C·D는 본문에 넣지 말고 마스터 판단으로 올린다.**

### 4-A. (본문 반영 권고) 슬라이더 재정렬 범위는 "이미 뽑힌 카드 안"이다

`app/api/recommend/route.ts:342-345`가 서버에서 가중치를 반영해 정렬한 뒤 **상위 10개만 잘라** 응답하고, 클라이언트의 `components/AiRecommendSection.tsx:102-106`(`sortedItems`)은 그 10개만 다시 정렬한다. 게다가 `:115-122`의 `dirty` 판정에 **가중치는 들어가지 않는다**(예산·기준연도·최소 세대수만) — 슬라이더를 아무리 움직여도 "다시 추천 받기" 안내가 뜨지 않는다.

→ 즉 **"어떤 10개가 카드가 됐는가"는 '추천 받기'를 누른 순간의 슬라이더 기준이고, "카드에 적힌 점수와 순서"는 지금 슬라이더 기준**이라 둘의 시점이 다르다. 발행본 `ai-recommend-weights-howto:482`·`:515`는 "추가 조회 없이 바로 순서가 다시 매겨진다"까지만 말하고 이 범위 제한은 서술하지 않는다. 독자 효용이 크고 **동작 자체는 의도된 설계**(무호출 재정렬)이므로 결함 보고가 아니다. → [15]에 반영.

### 4-B. (본문 반영 권고) '신축 기준연도'는 점수 입력이자 후보 제외 문턱이다

`app/api/recommend/route.ts:195`가 `newbuildScore(...) < 40`인 단지를 **후보에서 아예 제거**한다. `lib/recommender.ts:131-135`상 기준연도보다 10년 이상 오래된 단지가 여기에 해당한다. 발행본 howto `:474`는 "연도를 낮추면 더 오래된 단지까지 신축 점수를 받게 된다"고만 적어 **필터로도 작동한다는 사실이 라이브 어디에도 없다.** → [15]에 한 구절로 반영(구체 점수·연수는 쓰지 않는다, §6).

### 4-C. 🔴 (본문 제외 권고 · 마스터 판단 필요) 발행본 howto의 '측정불가' 설명이 코드와 어긋난다

발행본 `lib/blog.ts:518`:

> "평지 항목이 '측정불가'로 뜨는 것은 **해당 단지의 고도 데이터가 없다는 표시**이며, 오류가 아닙니다."

코드는 그렇지 않다. 추천 경로에서 `slope_score`가 `null`(= 카드의 '측정불가', `components/RecommendCard.tsx:104-111`)이 되는 조건은 **좌표 미확인 하나뿐**이다:

- `app/api/recommend/route.ts:281` — `withCoord = filled.filter(({geo}) => geo.lat != null && geo.lng != null)`, 즉 좌표가 있는 단지만 경사 계산 대상.
- `:324` — `slopeMap.get(...) ?? null`, 맵에 없으면(=좌표 없으면) `null`.
- `lib/recommender.ts:342-359` — `getSlopeScore`는 **어떤 경우에도 `null`을 반환하지 않는다.** 고도 자료가 모자라면(`elevations.length < 3`) `50`을 반환한다.

→ **고도 자료가 없을 때는 '측정불가'가 아니라 점수가 채워진다.** 발행본 문장은 원인을 반대로 적고 있다. 같은 오해가 `lib/recommender.ts:27-29`의 타입 주석("고도 데이터 확보 실패… 시에만 null")에도 남아 있다.

- **왜 문제인가**: 이 편의 [13]-③이 "고도 자료가 모자라면 값이 채워진다"를 서술하는 순간, **같은 사이트의 두 글이 같은 화면을 정반대로 설명하게 된다.** `aggregation-period` 편의 §4-3(옛 열 라벨 2편 불일치)과 같은 유형이다.
- **기획팀 권고**: §9 미결 3번 — 그때와 같이 **`lib/blog.ts:518` 1줄 정정 동반**(마스터가 그 선례에서 "라이브에 떠 있는 사실 오류"라며 예외 승인한 전례가 있다). 다만 이 편이 원인(좌표/고도)을 **명시하지 않고** 사실만 쓰는 회피안도 가능하므로 마스터가 택한다.
- 기획팀은 코드를 고치지 않는다. `recommender.ts:27-29` 주석 정정은 개발팀 몫으로 남긴다.

### 4-D. 🔴 (본문 제외 권고 · 마스터 판단 필요) '측정불가' 항목은 종합점수에서 0점으로 계산된다

`components/RecommendCard.tsx:38` `const slopeRaw = item.slope_score ?? 0;` — 같은 대입이 `components/AiRecommendSection.tsx:40`, `app/api/recommend/route.ts:335`에도 있다(세 곳 일치, 코드 주석은 "원본 규약대로 0 대입").

즉 **화면에는 '측정불가'로 점수를 감추면서, 종합점수 계산에는 최저값으로 참여한다.** 분모(가중치 합)에서 빠지지도 않는다. 그 결과 평지 비중을 올릴수록 좌표를 확인하지 못한 단지가 아래로 밀린다.

- **판단이 갈리는 지점**: 세 곳 구현이 일치하고 원본 이관이 명시돼 있어 **의도된 동작**으로 볼 근거가 있다(→ 원칙으로 서술 가능). 반면 화면 표기('측정불가')와 계산 취급(0점)이 어긋나 **결함 보고로 읽힐 소지**도 있다(→ `aggregation-period` §9 미결 4번과 같은 유형이며, 그때 마스터는 "본문 제외 + 개발 티켓"으로 판정했다).
- **기획팀 권고**: 위 선례를 따라 **본문 제외 + 개발팀 확인 티켓**(§9 미결 4번). [13]-③은 "고도 자료가 모자라면 값이 채워진다"까지만 쓰고 0점 대입은 언급하지 않는다. 마스터가 "의도된 동작이니 서술하라"고 판정하면 [13]에 한 구절 추가한다.

## 6. 썩는 정보 배제 — 임계값 수치를 본문에 쓰지 않는다 (판단 + 근거)

**결론: 점수 구간의 구체 임계값(거리 m·점수·구간 개수)을 본문에 한 건도 쓰지 않는다.** 원칙 4는 "구간으로 끊어 준다"는 **성질만** 서술한다.

근거 4가지:

1. **화면에 없는 내부 값이다.** `aggregation-period` 편에서 마스터가 기간 숫자 인용을 허용한 조건은 **"화면 라벨을 축자 인용하는 따옴표 안에서만"**(그 기획안 §9 확정 2)이었다. 거리 구간·점수 값은 카드·폼 어디에도 표시되지 않는다(`RecommendCard.tsx`는 점수와 거리 실측값만 그린다). `blog-ranking-board-usage-howto.md` §3 배제 목록 3(화면에 없는 내부 값 금지)의 선례가 그대로 적용된다.
2. **바뀌면 즉시 거짓이 되고 독자가 검증할 수 없다.** 구간 경계는 `lib/recommender.ts:106-112`의 상수일 뿐이고, 이 저장소는 실제로 산식을 손댄 이력이 있다(2026-07-15 `w_slope` 복원으로 항목이 3개→4개가 됐다). 카드에 임계값이 표시되지 않으므로 독자는 본문이 낡았는지 알 방법이 없다.
3. **논지가 숫자 없이 완전히 성립한다.** 원칙 4가 남기려는 것은 "① 구간 안에서는 차이가 사라지고 ② 경계에서는 작은 차이가 점수를 가른다 → 그러므로 **점수 차를 거리 차로 되돌리지 마라**"이며, 이 셋 중 어느 것도 300m나 85점을 필요로 하지 않는다. 오히려 표를 실으면 독자가 표를 외워 **점수에서 거리를 역산하려 들게 되어 원칙과 반대 방향으로 유도**한다.
4. **YMYL 관점.** 임계값 표는 "몇 미터 안에 들면 몇 점"이라는 최적화 지침처럼 읽혀, 참고 지표를 우열 기준으로 굳히는 효과가 있다(`content-strategy.md` §4 "우위 매기기" 취지).

**같은 원칙으로 본문에서 뺄 숫자 목록**(개발팀이 임의로 되살리지 말 것):

- 거리 구간 경계와 구간별 점수, 구간 개수 / 신축 점수 구간과 연수 / 고도 범위 구간 / **고도 자료 부족 시 채워지는 값(중간값)의 실제 숫자**.
- 후보 풀 크기, 한 회차 채움 상한, **카드 개수**. 특히 카드 개수는 채움이 덜 된 회차에 더 적게 나올 수 있어(`route.ts:345`는 `slice`이므로 10개 **이하**) 숫자로 단정하면 거짓이 될 수 있다 → "정해진 수만큼", "위쪽 몇 개"로 쓴다.
- 가중치 기본값(45/35/20/10)과 환산 백분율 예시 — `RecommendForm.tsx:157-160`이 화면에 백분율을 표시하지만, 기본값 자체는 상수라 바뀔 수 있다.
- 실제 지역명·단지명·금액·건수·점수 값, 수집 진행률·px·발행 편수 등(insight 관행).

**허용하는 UI 문자열 인용**: 카드에 실제로 찍히는 표기 두 개 — `도보 미확인`(`RecommendCard.tsx:59`), `측정불가`(`:109`). 게이트 예외 ②에 해당하며, 원칙 5가 성립하려면 이 두 표기를 짚어야 한다. 그 외 화면 문구는 인용하지 않는다.
